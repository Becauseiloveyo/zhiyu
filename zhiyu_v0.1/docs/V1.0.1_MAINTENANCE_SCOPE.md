## 2. START-001：证据、归因与方案选择

### 2.1 当前契约链

检查依据为[release_profile.py](../tools/release_profile.py)全文件、[release_recovery.py](../tools/release_recovery.py)、[开发 Compose](../docker-compose.yml)、[Reference 配置](../config/reference-profile.json)、[安装](INSTALLATION_GUIDE.md)与[部署指南](DEPLOYMENT_GUIDE.md)。

| 证据位置 | 实际行为 | 归因意义 |
|---|---|---|
| release_profile.py:124–151 | project 必须是 zhiyu-v1 登记格式，owner=project；Compose 由 deployment metadata 的 project 与 compose.private.json 定位 | 操作对象是特定部署，不是全 Docker 任意容器 |
| release_profile.py:153–186 | owned_database 用 compose ps -q postgres；未运行报 reference_database_not_running；refresh 同样要求 ingress 运行、owner 相符、实际回环端口有效 | 依赖检查发生在 API 启动前 |
| release_profile.py:365–427 | install 生成 owned 服务/网络/卷后，显式 up postgres ingress，再 refresh | 底层创建/启动责任在安装路径 |
| release_profile.py:477–488 | start_api 先 refresh，再 compose up api，然后等待 /ready | API depends_on 不能救此前已经失败的 refresh |
| release_profile.py:766–769 | start 调 start_api；stop 仅 stop api | 常规 stop/start 循环原本保留底层基础服务 |
| release_recovery.py:181–193 | 新恢复环境显式 up postgres ingress，再 restore/upgrade/start_api | 恢复工具也承认 infra 前置顺序 |
| docker-compose.yml | 开发 migrate/bootstrap/API depends_on；与安装生成的私密 Reference Compose 不同 | 不能套用开发 Compose 宣称 Reference start 会冷启动全栈 |
| INSTALLATION_GUIDE.md:83 | stop 只停 API；start 更新实际 PG 映射后启动 API | 支持 API 级 start 解释，但 stopped 先决条件不足 |
| DEPLOYMENT_GUIDE.md:25 | “Docker 重启后执行 start” | 文档给了超出当前实现的操作预期，真实矛盾必须修正 |
| [走查](FULL_PRODUCT_WALKTHROUGH_v1.0.0.md) | PG/ingress 都停止时失败；先人工恢复 owned infra 后正式 start/status/health/ready 成功 | 不能说原冷启动成功；也不是运行依赖齐全时 API start 失效 |

**主分类选择 B：documentation / bootstrap contract defect。** 当前实现与 stop/start 配对共同定义的是“已安装且基础服务运行时启动 API”；没有既有公开 infra-start 子命令，内部 bootstrap 是数据库/控制环境初始化，不是拉起 Docker 基础服务。正式部署指南的重启说明造成契约错位。此归因不豁免现场可用性问题，OPS-START 仍保留失败。

若负责人今后明确把“底层全部停止后 start 必须拉起全栈”定为正式产品合同，应将其转成新启动行为需求及相应实施缺陷修复；当前不能假定该合同已经存在，也不能以增加自动启动为唯一修法。

### 2.2 A/B/C 比较

| 方案 | 收益 | 代价 / 风险 | 本次建议 |
|---|---|---|---|
| A：start 自动启动 owned PG/ingress/API | 一个入口恢复 stopped 全栈 | 改变 start 副作用/责任范围；需处理锁、残缺部署、镜像/网络/卷身份与失败回滚，避免 Compose 隐式新建或拉镜像 | 不纳入 v1.0.1；Track C 在明确一键恢复需求后评估 |
| B：新增 bootstrap / infra-start | 管理员职责显式 | 增公开命令与权限表面；bootstrap 已有初始化含义，容易误用/重复初始化 | 不纳入 v1.0.1；如未来批准，应避免与现有 DB bootstrap 混名 |
| C：保留 start，明确 preflight/恢复提示 | 维护现有行为；把底层 stopped、missing、foreign、port 错误转成可理解诊断 | 仍需管理员先恢复 infra；必须文档与现场流程一起验收，不能只美化报错 | **推荐；诊断改进 SHOULD FIX，契约与恢复说明 MUST DOCUMENT** |

### 2.3 C 的可审阅设计（尚未实施）

1. 读取本 deployment 的受保护 metadata 与 Compose identity；仅检查允许的 project、owner、服务名、固定镜像/网络/卷及回环发布约束。诊断只输出非敏感状态，不打印 password、token、私密 Compose 全文或数据库 URL。
2. 用项目限定的 Compose 服务查询区分 RUNNING / STOPPED / MISSING；需要 stopped 识别时查询包含 stopped 服务，并交叉核对 `zhiyu.owner`、Compose project/service labels 与 deployment metadata。动态容器 ID 只能作为上述筛选后的内部证据，不硬编码、不由用户随意指定。
3. RUNNING + 合法时走原 refresh/API start/ready；STOPPED 返回“先由可信操作员恢复此部署 postgres/ingress”的可操作提示；MISSING/foreign/重复服务/身份不一致直接拒绝，不能转 reinstall、创建新卷或启动别的项目。
4. 恢复说明只针对已安装的既有 owned 服务：管理员先核对归属、既有数据卷及内部网络，再用该 project + 该 compose 文件 + 固定 postgres/ingress 服务名恢复；不使用 `docker start <任意ID>`、不 `down -v`、不自动迁移/清库、不打开 Worker/模型/Lab。
5. 管理员确认 PG healthy、ingress 固定监听及真实回环端口后，重新执行官方 start/status，再确认 /health 与 /ready、重新登录/快照。ingress healthy 不等于数据库/API ready。恢复命令需在批准后的隔离副本实际演练，演练前不能称流程已验收。
6. Preflight 缺依赖时不得写配置或产生 Docker 启停副作用；成功路径仅保留当前工具所需私密连接刷新与 API 启动。多个 Docker 项目/锁/在途任务场景必须拒绝危险捷径，不为了诊断让 start 获得额外权限。

## 4. 明确排除

Assets/Threats/Detection/Investigation 新页面，审批管理 UI，HTML/PDF 报告，Model/Worker 监控，HA、多租户、新 Sensor/模型/Agent/数据库/工作流，图引擎重写，ai.5 或 schema 改动全部排除。没有新需求就不建设；有需求也只能 Track C/D 重新评审。

大规模分页、冷安装重复、新宿主、真实 DB 服务故障、损坏档案恢复不是 F22 小数据补验的替代名称，也不自动塞入维护。已有损坏备份拒绝测试不能包装为完整灾难恢复。

## 5. 未来实施顺序与出口

批准维护后才依次执行：核对六项合同 → 文档修正与 C 方案最小诊断 → UI 四箭头修复 → 隔离 F22 补验 → 有意义的定向测试/浏览器检查 → 一次与实际变更相称的正式回归及发行复核。任何失败先停候选、保留旧版本，不覆盖原证据或改测试迎合实现。
