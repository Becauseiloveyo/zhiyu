## 2. 不应直接交给浏览器的内部/写 API

已有写接口保留并继续使用原安全链，未来产品 viewer 不获得其权限：

- ingestion：`POST /v1/events/batches`、`/raw-batches`，以及 `/v1/intelligence/process`。展示不能提交自称 OBSERVED 的任意日志。
- AI：构建 contexts、ai-analysis、plan-proposals、ai-decision、ai-replan。耗模型预算且可能产生计划，不能把 GET 展示刷新映射成这些 POST。
- execution：create plans/continuous-plans、claim、lease renew、authorizations、execute、worker tick。浏览器不持有 worker/service/admin token。
- verification：create、tick、decide、apply。独立身份必须由服务端配置；不能让 UI 自填 verdict 或冒用动作 Worker 进行验证。
- incident transition：目前只提供 TRIAGED/INVESTIGATING CAS，不是任意状态编辑器，不规划直接改 CLOSED/HUMAN_REVIEW 的展示后门。
- 非 HTTP 管理工具：Registry install、policy/admin、Lab control、Docker/DB reset、Audit verify 和 Outbox claim/ack。它们不是因有函数就可公开的 UI API；Audit.verify_chain 会锁 head，不得在每次 read overview 中执行。

## 4. Environment / Scope / 字段权限设计

源码 [ServicePrincipal](../src/zhiyu/core/identity.py) 只检查 environment_ids 与 permissions；现有 read routes 的 “scoped” 大多指 environment。Scope 的动作授权检查不等于 viewer 读权限。

规划新增内部 `ProductAccessPolicy`（服务器受保护配置，非 ai.5 新字段）：principal → environment → allowed_scope_ids/可见资源与审计权限。每个 endpoint 先验环境，再验服务端 grant；客户端 scope_id 仅缩小范围，绝不授予范围。没有 scope grant 且未显式授予环境全量 reader 时拒绝，不能默认返回全环境。

- Incident 无 scope_id：以当前 reader grant 和全部关联资源/对象的事实做可见性计算。第一版采用保守完整对象策略：混合授权范围或未知绑定的 Incident 不向局部 scope viewer 返回完整对象；只有获授环境全量可见权限才能看未绑定对象。不默默删字段后继续返回全局计数。边界/排除原因可返回不泄密的 coverage summary。
- EnvironmentRef、Evidence/ModelRun 等子对象必须沿显式关联回到已授权 Incident 或资源。只拿一个合法 incident_id 不能夹带其他环境 Evidence ID。
- 历史授权/Scope 过期用于解释历史动作；当前读可见性使用当前权限。历史 Scope 不是新执行凭证，也不是自动扩大 viewer 可见性的凭证。
- 对不存在和越权 ID 的响应保持一致；cursor 与 cache 键绑定 env、grant version、scope、过滤条件、排序、mode、snapshot。权限撤销后缓存也不可读。
- 不返回 raw_records.content、任意数据库配置、服务令牌、模型 key、保护 target token、完整 scope network 配置、未裁剪输入/输出、宿主路径或可直接访问的 db:// URI。对 source refs 输出可鉴权对象 ID，不自动 dereference 外部 URL。
- AI/sensor/actor 文本视为不可信数据，长度限制、转义和编码由 API 契约规定；未来渲染不执行 HTML/Markdown 脚本、公式或外链。展示用 redaction 不改写原 Evidence/hash。
- 浏览器身份接入是 M9.2 的技术设计点：使用低权限 viewer 与服务端 broker；operator 与 worker 凭证只在服务端。不能把当前 service token 烘焙进前端。认证方案随部署评审确定，不需要现在选择前端框架。

## 5. Snapshot consistency 和分页

`get_db()` 是普通 Session，未设置 REPEATABLE READ；几个现有 GET 串起来不是一致性快照。AIStateSnapshot 是模型范围的裁剪事实，不能代替完整报告快照。

规划规则：

1. 单个聚合请求使用短时 PostgreSQL `REPEATABLE READ READ ONLY` 事务，固定 `as_of`、可见性策略版本和 audit head；不锁核心写路径。时间窗与数据库事务快照是不同概念。
2. 普通 LIVE 列表用 keyset、固定创建时间+ID排序，响应声明 `consistency=LIVE_PAGE`。状态筛选下跨页并发更新可改变成员；不得仅靠截止时间/最大 ID/audit sequence 宣称严格一致。clock_timestamp 不是 commit timestamp。
3. Timeline/Graph/Report 需要同一画面数据快照时，由服务端在短事务内生成**有界** DTO snapshot，临时缓存已裁剪结果及 hash。返回 snapshot_id，TTL 起始建议 5 分钟；跨页读此不可变材料。过期返回 410，不能悄悄换到新快照。
4. 大报告超出单快照预算时显式 `TRUNCATED`/要求缩小窗口，或后台按预先冻结的 ID+内容衍生材料分块生成；不能跨独立查询拼接后标成一个 DB snapshot。UI/API 不持有跨 HTTP 的长数据库事务。
5. snapshot 是可丢弃衍生缓存，不作为新权威事实表。正式 report artifact 才长期封存；快照丢失不重放 Action。不增加事件流/第二套数据库。

## 6. 性能边界（待实现验证的初始配置，不是已测 SLA）

| 能力 | 初始上限 | 达限行为 |
|---|---|---|
| 普通 collection | default50/max200；AI default20/max100；响应≤1 MiB | cursor/summary；413/422 或 truncation，不返回 100000 Events |
| Timeline | 默认近24小时；允许更早窗口但一次≤7天；50/max200；快照最多2000 entries | 按窗口/分页检索，记录历史不完整和省略数 |
| Graph | 200 nodes、400 edges、depth≤2、证据引用每元素≤20摘要 | 返回 truncation/frontier token；不可只保留成功路径而丢矛盾 |
| Overview/health | 同步查询预算2秒起、输出≤256 KiB；viewer并发2/env总8起 | timeout/429 和 Retry-After；缺失值不变0 |
| Report | 一次 Incident/Scenario、默认最多7天、10000摘要行、10 MiB导出起、每env1个job | 提示缩小范围或受控分块；不影响安全 Worker 的保留容量 |

先用现有 env/incident/time、group/member、request/context 等索引；对候选 SQL 用未来 `EXPLAIN (ANALYZE, BUFFERS)` 在独立 Lab 评估 100k events/相关 Task/Evidence 数据，避免 N+1、全 JSONB 拉取、逐行构建计数。对 `intelligence_metrics`、`capacity.snapshot` 不做无界复用；SQL 分组保持相同统计定义。只有查询计划证明瓶颈才提出专用复合索引 migration，不先建物化投影表。

初版采用有界按需查询/轮询语义；不强推 WebSocket、事件总线或 Outbox 消费者。轮询周期由负载验证和后续交互设计决定。
