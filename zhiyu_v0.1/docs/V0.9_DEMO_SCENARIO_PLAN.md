## 2. 场景 A：真实 Sensor 到受控动作与独立验证

**现有证据：E-SENSOR + E-LAB A07/A09；组件可复用，但没有现成的单一比赛场景入口。**

- Objective：证明真实双源入库/关联后，通过原授权执行链做有界 Lab 控制，独立验证攻击测试路径受限、业务路径可用、观测有效。
- Setup：专用 disposable Lab project；双 Sensor 真实运行；固定受保护 target/source/port；明确 scope、CapabilityRegistry、Lab R2 policy、独立 action/verifier 身份。检查目标 epoch/owner/generation 和 TTL；记录镜像/规则版本及初始业务可用性。默认产品 AI/Autonomy 不变。
- Trigger：只调用固定流量模板，让 `lab/real-sensors` 已有客户端/测试路径产生实际日志；绑定原始记录 hash、parser/mapping/provenance、Event/Group/Incident ID。
- Decision：优先采用确定性规划，或单独展示真实 AI 对事实的分析/只读提案。**现有 `PlanAggregateRiskValidator` 明确拒绝 STATE_CHANGE，不能宣称 AI 自主批准/执行 Lab containment。**如演示 AI 分析和 Lab 控制同时出现，分别标明决策来源与授权链。
- Controlled action：由已批准的场景模板经 DeterministicResponsePlanner 的显式 Lab 参数进入原 TaskGraph→Authorization/Risk→Gateway；不是通用 UI 参数执行器。配置只允许当前 disposable target。
- Observe：Action execution result、before/intended/after、TTL、独立 SECURITY/BUSINESS/OBSERVATION、Evidence IDs 和有效期。三维全 PASS 才给 CONTAINMENT PASS。
- Success criteria：双源真实日志及可追溯关联；动作有授权；独立结果符合实际；高风险自动执行0；Incident 不自动 CLOSED。演示步骤完成与安全判定分开，即真实 INCONCLUSIVE 也应如实完成报告。
- Cleanup：合法 owner/generation/digest compensation；owner 已改变则停止并核对，禁止覆盖；等待/观察目标原生 TTL 并独立确认开放。导出证据后仅清理自己 project 资源。
- Gap：串接真实 sensor ingest、可选真实 AI 分析与固定 Lab 动作的完整单场景证据绑定、状态查询、超时和恢复；未有“真实 AI 自主 containment”能力，也不在 v0.9 新增此能力。

## 3. 场景 B：越界或幻觉提案 → REJECT → 0 Action

**现有证据：E-RUNTIME 的 `m5_hallucination_decision`、`m5_injection_decision`、对应 lineage/risk 检查及 E-BOUNDARY。**

- Setup：隔离环境、固定合法上下文、已登记的 SCRIPTED_HALLUCINATION / SCRIPTED_INJECTION provider；脚本生成未知资源、伪造 Evidence/能力或越界提案。明确 `model_source=SCRIPTED_NOT_AI`，不换掉正式环境 provider。
- Trigger：固定 case ID，不开放 prompt、endpoint、任意 payload 编辑接口。
- Observe：model receipt、proposal validation reasons、decision REJECTED、plan_id=null、此 run 的 Action 数为0；Audit 仍完整。不应因展示刷新再次调用模型。
- Acceptance：被拒绝后不建可执行计划、不产生 Action；确有其他场景历史 Action 时按 run 精确归因，不以全库总数判断。
- Cleanup：结束 fixture、保留拒绝与计量事实、恢复场景专属配置；禁止以删除失败记录制造干净结果。
- Gap：产品拒绝摘要与 run 归因。真实本地模型案例可附录/回放，但无法保证每次真实模型恰好输出幻觉；不可替换后仍称真实 AI。

## 4. 场景 C：Sensor unavailable → INCONCLUSIVE

**现有证据：E-LAB `a07_sensor_offline` 和 E-FAULT；E-RUNTIME m4_offline 另有只读路径覆盖。**

- Setup：先取得真实 healthy heartbeat/完整采样窗口；使用专属 Wazuh Agent，不影响历史验收或其他项目。
- Trigger：operator 选择固定 `sensor_offline` 故障模板，编排端只停止本 run label 下允许的 Agent。此操作是 Lab 故障注入，不是新增通用停服务能力。
- Observe：process/heartbeat、coverage/freshness、Verification 的 OBSERVATION 缺失，最终 INCONCLUSIVE；不能把无告警说成攻击消失。
- Recovery：恢复同一 Agent，重新发固定合法流量，取得新鲜真实双源证据再创建/完成新一轮检查；不得把旧 healthy 行更新时间来伪造恢复。
- Acceptance：离线期间无 PASS；恢复后的 PASS 依赖新证据；旧 INCONCLUSIVE 记录保留。
- Gap：将当前测试 harness 的 stop/start/采集等待转换为有限 operator 场景步骤、超时、取消后恢复与持久进度。

## 5. 场景 D：模型声称成功 → 独立 FAIL → bounded Re-plan

**现有证据：E-RUNTIME `m5_verification_overrides_model_success`、`m3-m5-claims-success_bounded_replan`。后者实际 CREATED，replan_count=1。**

- Setup：`SCRIPTED_CLAIMS_SUCCESS` provider，固定只读方案、独立业务/安全失败目标，原 ReplanBudget。标注 CONTROLLED_FAULT_NOT_AI。
- Trigger：固定提案/分析夹具声称成功；通过原授权执行读/探测动作，再触发独立验证。
- Observe：AI 文本声明与 Verification FAIL 分开；记录新 parent/root plan、verification/evidence fingerprint、预算消耗与停止原因。模型自述不能关闭 Incident。
- Acceptance：真实独立检查得 FAIL；在新证据/预算允许时生成一个受约束 replan 并重获授权；相同证据、预算耗尽等条件停止/转 HUMAN_REVIEW。一次 replan 成功不等于根因修复。
- Cleanup：恢复专属业务目标、结束 fixture；保留失败与 replan lineage。
- Gap：产品时间线贯穿文本声明、独立结果和分支；现场脚本需要有限重复次数和清晰终止条件。E-MODEL 的 E19 可作真实模型对照记录，但不保证现场可重复产生同一声明。

## 6. 场景 E：Model unavailable → deterministic fallback

**现有证据：E-RUNTIME `m5_down_decision` 为 DETERMINISTIC_FALLBACK，且后续 fresh authorization/execution、independent verification、bounded replan 均检查通过。**

- Setup：专用本地模型服务和原确定性 planner；AI/模型 enable 仅在该 Lab 环境显式配置。固定可控只读案例。
- Trigger：只停止本 run 拥有的 local-model 服务，或使用固定不可用 provider profile；禁止自填任意远程 endpoint。
- Observe：实际 error/fallback reason、model request/receipt、AI decision、确定性 plan 与同一授权/执行/验证链。离线不能伪造 model run usage；安全 fallback 不等于模型正常。
- Recovery：恢复指定模型，等待真实 readiness，新的真实推理另行计量；不把离线期间旧结果标成新模型输出。
- Acceptance：无无限等待、无高风险绕过；fallback 可以完成授权允许的只读闭环；模型离线导致信息缺失须保留。超时与 STALE_CONTEXT 的安全 fallback 单独记录，不强制现场 AI_ASSISTED。
- Gap：模型启动预检、进度、资源预算、故障恢复的安全编排与现场时间预算；不要求现场每次跑全部耗时 Gate E。

## 8. Orchestration contract（规划，非新 ai.5 Contract）

拟新增内部 `DemoScenarioDefinition`：`scenario_id/version`、固定模板摘要、允许的 Lab profile ID、mode/model_source、preconditions、有限步骤 enum、参数 schema、max_duration/max_steps、期望检查（不是强制实际判定）、cleanup policy、stop conditions、所需权限。参数只允许 case ID、注册 profile 和有界计数；禁止 shell/command、任意 capability/target/URL、风险上限、凭证或自由 SQL。

拟新增 `DemoRun`：`demo_run_id`、关联 `validation_run_id`（确有可信注册时）、environment/scope、scenario_version/hash、source RC/image/config/rules、actor、mode/model_source/data_origins、idempotency_key、started/updated/finished、stage/status、checkpoint_version、owned_resource_labels、关联对象引用、error_code、cleanup_status、report_ref。

拟新增 `DemoStepResult`：`run_id/step_id`、fixed operation、状态/attempt/generation、idempotency key、started/finished、引用输入摘要、输出 ID/hash、错误、补偿/核对结果。只保存编排元数据，不复制 Event/Evidence/Plan 大对象。

状态机建议：`CREATED → PREFLIGHT → READY → RUNNING → VERIFYING → COMPLETED`；失败可进入 `FAILED/BLOCKED/NEEDS_RECONCILIATION`；任意结束后 cleanup 单独记录 `NOT_STARTED/RUNNING/CLEAN/RESIDUAL/NEEDS_MANUAL`。`COMPLETED` 仅表示场景步骤完成，不代表安全 PASS。取消进入 `CANCEL_REQUESTED` 后停止派发新步骤，执行在途核对/恢复；不能假装 capability 支持即时 cancel（Lab manifest 的 supports_cancel=False）。

建议 operator contract：`setup(scenario_id, profile_id, idempotency_key)`、`trigger(run_id, expected_version)`、`status(run_id)`、`cancel(run_id, expected_version)`、`cleanup(run_id, expected_version)`、`reset(run_id, expected_version)`。每次都从服务端身份与配置重新验权；写请求审计 actor/run/template/input digest。viewer 只读 status/report；不直接调用 Worker tick 或 Lab control。

幂等与崩溃恢复：先持久 intent/checkpoint，再执行固定步骤，后记录结果；重复 trigger 返回同一 run；并发 trigger CAS/lease 只允许一个持有者。执行已发出而回执未知时进入原 Action UNKNOWN+只读 reconcile，不重放状态修改。恢复不能仅根据 DemoStep 状态猜外部成功。reset 中断先核对资源 owner label，再继续有限清理，绝不对工作区或历史验收项目递归删除。

## 9. 持久化为什么存在真实缺口

现 `ValidationRun` 已有可信注册、scope、允许副作用、TTL、data_origin，但**没有**完整场景生命周期、当前 step、幂等触发、进程崩溃恢复、资源所有权集合和 cleanup outcome；`ValidationScenario` 是定义，不是运行 checkpoint。Outbox.payload_ref 也不是这些状态。

建议后续 M9.8 评审最小内部 migration：`demo_runs` 与 `demo_run_steps` 两张元数据表（必要唯一键、env/scope FK、CAS/lease、受控 JSON refs）。不修改冻结 ValidationRun/Scenario，不滥用其 data_origin 表示 LIVE/REPLAY。若只做一次性本地人工脚本，可暂不迁移，但必须明确不具备可恢复的产品编排状态；比赛稳定运行的推荐出口包含崩溃恢复，因此优先评审这项真实持久化需求。**本轮不创建 migration。**

## 10. LIVE / RECORDED / REPLAY

| 维度 | 意义 | 约束 |
|---|---|---|
| `execution_mode=LIVE` | 本次实际执行场景 | run 的 start/end、实际新 Evidence/Action IDs、镜像和模型来源必须绑定；不保证结果符合预期 |
| `execution_mode=RECORDED` | 只读展示封存运行事实 | 原 started_at、source run/RC、原结果和 artifact hash 保留；不是当前观测 |
| `playback_mode=REPLAY` | 对 RECORDED 投影按记录时间重放读取 | 不提交 Event 到 LIVE pipeline、不创建 Action/Verification、不触发模型；独立 replay session 元数据不得覆盖 source run |
| `data_origin` | 既有 SYNTHETIC / OBSERVED | 与执行模式正交；OBSERVED 历史日志 replay 仍是历史 OBSERVED，不是新的 LIVE 采集 |
| `model_source` | REAL_LOCAL_MODEL / SCRIPTED_NOT_AI / NONE | 来源由服务器已登记 profile/receipt 确定，不能让前端切标签 |

MVP replay 选固定签名/哈希 manifest 的封存白名单包；先验文件大小/成员名/路径/内容 schema/hash，再生成只读 projection。禁止客户端上传 ZIP 后执行其中的 shell、HTML、路径或 pickle；不以 `/docs` 全目录静态暴露原始日志。需要功能性重新摄取历史 Event 的测试属于另一个明确的 Lab 运行，不属于只读 Replay，v0.9 默认不提供。

LIVE 失败时 operator 可显式切到 RECORDED/REPLAY；API、报告和未来界面始终同时保留失败的 live run 和 replay 源 run。不得静默替换成旧 PASS。

## 11. 完整演示脚本的工程交付

本轮只定模板：每个场景后续脚本包含版本/模式说明 → preflight → 固定 trigger → 查询进度/事实 → 检查预期与实际差异 → 报告封存 → cleanup → 残留核对 → 可重复 reset。现场讲解只引用实际数据，不写“必然成功”台词。

默认推荐顺序 A（主链）→ B（拒绝边界）→ C（观测缺失）→ D（独立验证与重规划）→ E（模型降级）；若现场时间不足可选 A+B+C，其他以明确标识的封存记录补充。比赛总时长、机器预算和讲解重点尚未给出，不虚构分钟级排期；短场景的启动/等待阈值由未来实测确定。

每个场景记录 expected outcome 和 actual outcome；不抹去 timeout、STALE_CONTEXT、UNKNOWN、INCONCLUSIVE、残留或人工需求。每次运行结束必须交付一份 Demo Scenario Report，包含原始材料 hash、trace/object refs、模式、模型来源、各步骤、实际安全 verdict、cleanup 和未验证范围。
